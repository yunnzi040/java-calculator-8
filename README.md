# Java Calculator Precourse

## 구현 기능 목록

각 기능은 개별 커밋으로 구현됩니다.

### 1. 기본 입력 처리
- 사용자로부터 문자열 입력 받기
- `null` 또는 빈 문자열(`""`) 입력 시 `0` 반환
- 입력 문자열의 앞뒤 공백 제거(`trim`)

### 2. 커스텀 구분자 처리
- 입력 문자열이 `//`로 시작하면 커스텀 구분자로 판단
- `//`와 `\n` 사이의 문자를 커스텀 구분자로 추출
- 커스텀 구분자 지정 시 `\n` 이후 문자열을 본문으로 인식
- 커스텀 구분자를 기준으로 숫자 분리

### 3. 기본 구분자 처리
- 기본 구분자(쉼표 `,` 또는 콜론 `:`)로 숫자 분리
- 분리된 문자열을 정수로 변환
- 변환된 숫자들의 합계 계산

### 4. 예외 처리 (`IllegalArgumentException` 발생)

| 예외 상황 | 입력 예시 | 오류 메시지 |
|-----------|-----------|-------------|
| 커스텀 구분자 형식 오류 | `"//"` (구분자 없음) | "커스텀 구분자 형식이 올바르지 않습니다." |
| 구분자 비어있음 | `"//\n1;2;3"` (구분자가 비어있음) | "구분자는 비어있을 수 없습니다." |
| 음수 포함 | `"1,-2,3"` 또는 `"//;\n1;-2;3"` | "음수는 허용되지 않은 값입니다: [음수값]" |
| 숫자가 아닌 값 | `"1,a,3"` 또는 `"//;\n1;a;3"` | "숫자가 아닌 값이 포함되어 있습니다: [잘못된값]" |
| 빈 값 | `"1,,3"` 또는 `"//;\n1;;3"` | "빈 값은 허용되지 않습니다." |
| 구분자 혼용 | `"//;\n1,2;3"` | "커스텀 구분자와 기본 구분자를 혼용할 수 없습니다." |
| 잘못된 구분자 | `"1;2;3"` (기본 구분자 외의 `;` 사용) | "기본 구분자(, 또는 :)만 사용할 수 있습니다." |
| 일반 예외 | 예상치 못한 오류 발생 시 | "예상치 못한 오류가 발생했습니다: [오류메시지]" |

### 5. 출력 기능
- 계산된 합계를 콘솔에 출력

## 테스트 계획

각 단계별로 다음 테스트 케이스를 작성합니다.

- `null` 입력 → `0` 반환
- 빈 문자열 `""` 입력 → `0` 반환
- 공백이 포함된 입력 `" 1,2,3 "` → `6` 반환

### 2. 커스텀 구분자 처리 테스트
- `"//;\n1;2;3"` → `6` 반환
- `"//|\n1|2|3"` → `6` 반환
- `"//;\n1,2,3"` → `IllegalArgumentException` 발생

### 3. 기본 구분자 처리 테스트
- `"1,2,3"` → `6` 반환
- `"1:2:3"` → `6` 반환
- `"1,2:3"` → `IllegalArgumentException` 발생

### 4. 예외 처리 테스트
- 빈 값: `"1,,3"` → `IllegalArgumentException` 발생
- 숫자 아님: `"1,a,3"` → `IllegalArgumentException` 발생
- 음수: `"1,-2,3"` → `IllegalArgumentException` 발생
- 구분자 혼용: `"//;\n1,2;3"` → `IllegalArgumentException` 발생

### 5. 출력 기능 테스트
- 계산 결과가 콘솔에 올바르게 출력되는지 확인


## 코드 설계 과정

### 1차 코드 설계

> **왜 코드를 이렇게 작성했는지?**

하나의 메소드에는 한 가지 기능만 있어야 한다고 생각했기 때문에 **기능별로 분리**할 생각을 먼저했다. 그래서 아래와 같이 분리를 했다.

#### 설계 원칙
1. **중복 코드 제거**: `sum()` 메소드에는 공통 로직(숫자 합계)을 분리
2. **기능별 분리**:
   - `custom(String input)`: 커스텀 구분자 처리
   - `basic(String input)`: 기본 구분자(, 또는 :) 처리
   - `sum(String[] numbers)`: 숫자 합 계산 및 검증

#### 1차 설계의 한계점
하지만 예외 처리를 넣어보니 묘하게 복잡해보이고 메소드 간 흐름이 직관적이지 않다는 느낌이 들었다. 특히 커스텀 구분자와 기본 구분자 처리 로직이 각각 따로 존재하다 보니까 **'입력 → 구분자 추출 → 숫자 분리 → 합 계산'** 이라는 전체 흐름이 한눈에 들어오지 않았다.

그리고 각 기능이 한 메소드 안에 묶여 있어 단위 테스트를 진행하거나 특정 단계만 검증하기가 어렵다는 점도 느꼈다. 예를 들면, "커스텀 구분자만 정확히 추출하는지" 테스트를 하려면 `custom()` 전체를 실행해야 했다.

---

### 2차 코드 설계

1차 설계의 한계(흐름 직관성, 단위 테스트 용이성)를 개선하기 위해 2차 설계에서는 **단계별 책임을 명확히 나눴다**. 요구 사항 분석을 통한 기능 목록은 1차 설계할 때 만들어뒀으니 구조 설계만 다시 해본다.

#### 구조 설계
1. **`calculate(String input)`**: 입력 문자열을 받아 합계를 반환
2. **`extractSeparator(String input)`**: 입력에서 커스텀 구분자를 확인하고 반환
3. **`splitNumbers(String input, String separator)`**: 문자열을 구분자로 나눠 숫자 배열 생성
4. **`sumNumbers(String[] numbers)`**: 숫자 배열을 합산, 숫자가 아니면 예외 발생

#### 실행 흐름
calculate() → extractSeparator() → splitNumbers() → sumNumbers()


#### 2차 설계의 장점
- **흐름의 명확성**: 각 단계가 순차적으로 연결되어 전체 로직을 이해하기 쉬움
- **단위 테스트 용이성**: 각 메소드가 단일 책임을 가져 개별 테스트 가능
- **확장성**: 새로운 구분자 타입이나 검증 로직 추가 시 해당 단계만 수정하면 됨
- **재사용성**: 각 메소드를 다른 곳에서도 독립적으로 사용 가능
